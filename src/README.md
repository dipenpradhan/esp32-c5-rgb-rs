# src

The root binary crate — the firmware that runs on the ESP32-C5. One file,
`main.rs` (`#![no_std]`, `#![no_main]`), compiled for
`riscv32imac-unknown-none-elf`. It is the only binary of the `esp32-c5-rgb-rs`
package (auto-discovered from `src/main.rs`, no `[[bin]]` block), so a plain
`cargo build` / `cargo run` targets this.

It is a thin hardware layer: every effect, the WS2812 timing and the config
model live in `led-core/`. This file only wires the chip's RMT peripheral and
GPIO to `led-core`'s already-tested logic.

## What `main.rs` does

Startup, in order:

1. `esp_hal::init(...)` — bring up the peripherals; the `#[esp_hal::main]`
   attribute provides the chip's entry point. An 8 KiB heap is declared
   (`esp_alloc::heap_allocator!`) for `serde_json`/`alloc`.
2. Parse `configs/effects.json`, embedded at compile time with
   `include_str!("../configs/effects.json")`. A malformed config falls back to
   an empty `LedConfig` (the LED simply does nothing) rather than failing.
3. Configure the **RMT** transmitter on `channel0`, GPIO27, at 80 MHz so one
   tick is 12.5 ns. The WS2812 waveform is generated by the RMT hardware
   peripheral, not GPIO bit-banging.
4. Loop forever: for each effect in the config, drive the LED.
   - `blink` — send each colour, hold `duration_ms` between them.
   - `blend` — interpolate `from`→`to` over `steps` steps, `step_ms` apart
     (the interpolation is `led_core::color::interpolate`).

Each colour is one call into `ws2812_rgb_rmt`, which builds the 25-entry RMT
pulse-code frame (`frame_codes`, over `led_core::ws2812::encode_rgb_v2`) and
`transmit`s it. `transmit` consumes the channel and `wait()` returns it, so the
channel is threaded through the loop by value. Per frame the blocking time is
~330 µs (dominated by the 300 µs reset LOW).

The top-of-file doc comment records why the RMT: the earlier
`GpioPulse`/`replay_frame` driver timed only one phase per bit, so consecutive
`1` bits merged into a single HIGH pulse and the 24-bit GRB frame misaligned
(garbled colour). `delay_nanos` cannot fix it — it quantises to whole
microseconds, so all four phase widths (400/850/800/450 ns) round to 1 µs and a
`0` bit becomes indistinguishable from a `1` bit.

## Relationship to `led-core/` and `examples/`

- **`led-core/`** is the pure, host-testable logic crate (config model,
  WS2812 encoding, colour interpolation, HTTP and WiFi validation). This binary
  uses only `led_core::config`, `led_core::ws2812::encode_rgb_v2` and
  `led_core::color::interpolate`. `main.rs` does **not** call
  `led_core::ws2812::replay_frame` or anything `GpioPulse`-based — those are the
  legacy bit-bang path, kept in `led-core` only for its host tests. The firmware
  emits the waveform through the RMT instead. (A grep for `replay_frame` /
  `GpioPulse` across `src/` and `examples/` finds the names only in doc
  comments explaining the old driver, never in a call site.)
- **`examples/`** hold the other firmware binaries (product demos, diagnostics,
  the WiFi/web-server builds). They share the same thin-layer shape and, for the
  LED-driving ones, the same RMT code as here. See `examples/README.md`.

## Building and flashing

Commands are run from the repo root. `build.sh` and `.cargo/config.toml` are
the source of truth for the target and runner.

```bash
# One-command build (checks toolchain, seeds configs/wifi.json only if absent,
# then `cargo build`, then prints the artifact path and next steps):
./build.sh

# Or build directly (default features; target inherited from .cargo/config.toml):
cargo build
# -> target/riscv32imac-unknown-none-elf/debug/esp32-c5-rgb-rs
cargo build --release   # esp-hal recommends release for timing-sensitive use
# -> target/riscv32imac-unknown-none-elf/release/esp32-c5-rgb-rs
```

Flashing (needs `espflash`, and the default binary needs no `configs/wifi.json`
since it does not use WiFi):

```bash
# Uses the runner from .cargo/config.toml: `espflash flash --monitor --chip esp32c5`
cargo run

# Or explicitly, on a chosen port:
cargo espflash flash --chip esp32c5 --port /dev/ttyACM0 --monitor
```

Both `cargo build` and `cargo build --release` were run and succeeded here.
Flashing was not exercised (no board attached); the command forms above are the
ones `build.sh` and `.cargo/config.toml` document.

The default features enable **no** WiFi/Web deps, so the default binary does not
pull in the `esp-wifi-sys` blobs in `thirdparty/` (see `thirdparty/README.md`)
— those are linked only when building with `--features wifi` / `wifi-net` /
`webserver`.

## No host tests here

There is no `#[test]` code in this crate, and `cargo test` on the package cannot
run one. The reason is **not** `.cargo/config.toml`: it is that `esp-hal`'s
`build.rs` hard-refuses to build for any target other than the chip's
(`chip.target() != $TARGET` → it bails with "building for an unsupported or
wrong target"). `cargo test` needs the host target and its `test` harness, so
the build is refused before the harness is ever reached. The host-testable logic
lives in `led-core/` and is tested there (see `led-core/README.md` and
`scripts/test-led-core.sh`); this file is the untestable-on-host hardware layer.

## Known duplication

The RMT tick math — `ns_to_ticks` and `frame_codes`, plus the
`RMT_SCLK_MHZ` / `CHANNEL_CLK_DIVIDER` / `NS_PER_SEC` constants — is duplicated
byte-for-byte between `src/main.rs` (lines 49–98) and
`examples/web_server.rs` (lines 217–270); the two function bodies diff clean.
It is repeated in the other LED-driving examples (`led_effects_sync`,
`led_effects_async`, `wifi_led_test`) as well. It is a candidate for a shared
helper in `led-core` (it is pure, target-independent, and already host-testable
in spirit), but as of today it is copy-pasted per binary.

The channel clock divider is `1` (no division at 80 MHz). The doc comment
records that `0` is the register's special "divide by 256" default — so leaving
the divider at its default would make each tick 3.2 µs (12.5 ns × 256) and push
every WS2812 phase far outside its ±150 ns window. `1` was chosen deliberately
to keep the 12.5 ns resolution.
